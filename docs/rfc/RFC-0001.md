# RFC-0001: SLDS v0.1 — Short Link Domain Specification

| Field | Value |
|-------|-------|
| **Status** | Draft |
| **Version** | 0.1.0 |
| **Created** | 2026-10-08 |
| **Language** | Lua 5.1 / 5.3 / LuaJIT |

---

## 1. Abstract

SLDS (Short Link Domain Specification) defines the **identity**, **lifecycle**, and **resolution semantics** of short links, while remaining independent of transport, storage, caching, security policy, observability, analytics, and deployment.

**Compressed definition:**

> SLDS = Short Link Identity + Lifecycle + Resolution Semantics

SLDS is a pure Lua domain library — analogous to how `dkjson` is a JSON codec or `lua-MessagePack` is a MessagePack codec. It does not concern itself with HTTP routing, database access, Redis caching, or OpenResty integration. Those are Infrastructure Adapter concerns, layered *on top of* SLDS.

---

## 2. Iron Rules

These ten rules are the soul of the project. They MUST be placed at the very front of any implementation.

| Rule | Statement |
|------|-----------|
| **RULE-001** | SLDS Core MUST NOT depend on HTTP. |
| **RULE-002** | SLDS Core MUST NOT depend on a specific database. |
| **RULE-003** | SLDS Core MUST NOT fetch Target URLs. |
| **RULE-004** | Code MUST be immutable after creation. |
| **RULE-005** | Code uniqueness MUST be enforced atomically by the persistence layer. |
| **RULE-006** | Deleted Codes MUST NOT be reused by default. |
| **RULE-007** | Resolve MUST NOT require an external event/analytics system to succeed. |
| **RULE-008** | Analytics MUST NOT be part of the resolution critical path. |
| **RULE-009** | Authorization MUST be implemented outside the Core Domain. |
| **RULE-010** | Any implementation claiming SLDS compatibility MUST pass the applicable Conformance Test Suite. |

## 3. Core Domain Objects

### 3.1 Identity

The **Identity** answers the question: *"Who is this short link?"*

```
Identity = { namespace, code }
```

- `namespace` — logical partition (e.g., `"default"`, `"marketing"`, `"internal"`)
- `code` — the short code string (e.g., `"a8Kx2"`)

**Identity is NOT:** URL, Host, Domain, Tenant, User, Campaign, Database ID, or Redis Key. It is the minimal tuple that uniquely identifies a short link within the domain.

Identity is a **value object** — logically immutable after creation. Its Lua reference representation is an ordinary table: callers MUST NOT rewrite its fields, and operations MUST NOT mutate the caller object. Update APIs prohibit persistent identity changes; direct-assignment errors are not promised. Two Identity objects with the same namespace/code are equal.

### 3.2 ShortLink

The **ShortLink** answers the question: *"What does this Identity currently represent?"*

```
ShortLink = { namespace, code, target, status, expires_at }
```

- `target` — the destination URL string
- `status` — lifecycle status (see [§3.3](#33-lifecycle))
- `expires_at` — optional Unix timestamp; if set and `expires_at < now`, the link is considered expired

### 3.3 Lifecycle

The **Lifecycle** defines three persistent statuses:

| Status | Resolvable? | Description |
|--------|-------------|-------------|
| `ACTIVE` | Yes | Normal operational state |
| `DISABLED` | No | Temporarily disabled (can be re-enabled) |
| `DELETED` | No | Permanently removed (cannot be restored) |

**EXPIRED is NOT a persistent status.** It is derived at resolution time:

```
if expires_at and expires_at < clock:now() then
    status = "EXPIRED"  -- derived, not stored
end
```

State transitions:

```
         create
           │
           ▼
       ┌────────┐  update  ┌──────────┐
       │ ACTIVE │ ───────► │ DISABLED │
       └────────┘          └──────────┘
           │                     │
           │     update          │ update
           └──────► (back) ──────┘
           │
           │ delete
           ▼
       ┌─────────┐
       │ DELETED  │  (terminal — no transitions out)
       └─────────┘
```

### 3.4 Resolution

**Resolution** is the most important capability of SLDS. It is a **first-class domain operation**, not an alias for `Repository.get()`.

```
slds:resolve(ctx, identity) -> ResolutionResult
```

Resolution logic:

```
identity → Repository.get()
  │
  ├─ Not Found ────────────────► ResolutionResult{ found = false }
  │
  ├─ status = DELETED ────────► ResolutionResult{ found = true, status = DELETED } → not resolvable
  │
  ├─ status = DISABLED ───────► ResolutionResult{ found = true, status = DISABLED } → not resolvable
  │
  ├─ expires_at < now ─────────► ResolutionResult{ found = true, status = EXPIRED } → not resolvable
  │
  └─ status = ACTIVE, not expired ─► ResolutionResult{ found = true, target = ..., status = ACTIVE }
```

**Key principle:** Resolution is Read/Resolve Semantics, not Persistence Semantics. The domain decides *whether* a link can be resolved — the repository merely retrieves the data.

### 3.5 ResolutionResult

The **ResolutionResult** is the output of resolution. It does **not** expose the internal ShortLink entity.

```
ResolutionResult = {
    found      = boolean,   -- was the identity found in the repository?
    namespace  = string,
    code       = string,
    target     = string|nil, -- present only if resolvable
    status     = string,     -- ACTIVE | DISABLED | DELETED | EXPIRED | NOT_FOUND
    expires_at = number|nil,
}
```

**Why not return ShortLink directly?** Returning the raw entity would leak persistence details. ResolutionResult is a stable contract that can survive entity schema changes.

## 4. Operations

SLDS defines four **lifecycle operations** (not infrastructure CRUD):

| Operation | Signature | Description |
|-----------|-----------|-------------|
| `create` | `slds:create(ctx, input) -> ShortLink, err` | Create a new ShortLink Identity and Target |
| `resolve` | `slds:resolve(ctx, identity) -> ResolutionResult or nil, err` | Resolve an Identity; propagate infrastructure failures |
| `update` | `slds:update(ctx, identity, patch) -> ShortLink, err` | Modify mutable domain properties (target, status, expires_at) |
| `delete` | `slds:delete(ctx, identity) -> boolean, err` | Make an Identity permanently unresolvable |

### 4.1 Create

Input:

```
{
    namespace = "default",       -- optional, defaults to "default"
    code = "a8Kx2",             -- optional; if omitted, Generator+Encoder produce one
    target = "https://...",      -- required
    expires_at = 1760000000,    -- optional
    metadata = {},              -- optional; Core MUST NOT interpret
}
```

Behavior:

1. If `code` is provided (custom code), use it directly.
2. If `code` is omitted, call `Generator:generate(ctx)` to get an internal ID, then `Encoder:encode(id)` to produce a short code.
3. Call `Repository:create(ctx, link)` — uniqueness is enforced atomically by the repository.
4. Return the created ShortLink.

### 4.2 Update

Patch fields — **only mutable properties:**

```
{
    target = "https://new-url.com",   -- optional
    status = "DISABLED",             -- optional
    expires_at = 1760000000,         -- optional
}
```

**Code and namespace are immutable** — updating them MUST fail with a programming error.

Only supplied non-nil target/status/expires_at fields are committed. Repository MUST atomically validate against the latest record and preserve unspecified fields; a DELETED record at commit rejects updates with nil,DELETED. Different-field changes survive and same-field changes follow commit order; application-level read-modify-write conflict detection is not promised. Failed validation MUST leave storage unchanged. A Service pre-read is insufficient to establish these guarantees.

Metadata patches are unsupported and ignored, preserving existing metadata contents. A nil expires_at patch means unchanged; this version defines no expiration-clearing sentinel. Expiration MUST be a finite number when present; equality with now remains unexpired.

### 4.3 Delete

Logical deletion — sets status to `DELETED`. The record may remain in the repository for audit purposes, but resolution MUST return "not resolvable" for deleted links.

Per **RULE-006**, deleted codes MUST NOT be reused by default.

## 5. Ports (Boundary Contracts)

Ports are **interface contracts**, not implementations. SLDS Core depends on the interfaces; Infrastructure Adapters provide the implementations.

### 5.1 Repository Port

```
repository:create(ctx, link) -> link, err      -- create a new short link
repository:get(ctx, identity) -> link, err     -- retrieve by identity
repository:update(ctx, identity, patch) -> link, err  -- apply patch
repository:delete(ctx, identity) -> boolean, err      -- logical delete
```

SLDS does not care whether the repository is MySQL, PostgreSQL, Redis, SQLite, or MongoDB. The repository implementation MUST enforce code uniqueness atomically (RULE-005).

### 5.2 Generator Port

```
generator:generate(ctx) -> id, err    -- generate an internal unique value
```

The generator produces an internal unique identifier (e.g., a sequential number, UUID, or snowflake ID). This is **not** the short code — the Encoder transforms it into a short code.

### 5.3 Encoder Port

```
encoder:encode(id) -> code    -- convert internal value to short code
```

The host MUST select a Generator/Encoder pair with compatible ID representations. Generic ports MUST NOT impose the reference adapters' numeric limit, alphabet or code length.

The encoder is a **pure transformation** — it does not need `ctx` (no I/O, no side effects). Examples: Base62 encoding, Base64 encoding, hash-based encoding.

## 6. Hooks (Extension Mechanism)

Hooks are the **extension mechanism** for observability — they are NOT part of the SLDS core domain.

```
slds:use(hook)
```

A hook is a Lua table with optional callbacks:

```
{
    before_create = function(ctx, input) end,
    after_create  = function(ctx, link) end,
    before_resolve = function(ctx, identity) end,
    after_resolve  = function(ctx, result) end,
    before_update = function(ctx, identity, patch) end,
    after_update  = function(ctx, link) end,
    before_delete = function(ctx, identity) end,
    after_delete  = function(ctx) end,
    on_error      = function(ctx, err) end,
}
```

Logger, Metrics, Tracer, and Audit are **implementations** of hooks, not SLDS core. SLDS provides the injection points; the application layer provides the behavior.

**Key principle (RULE-007, RULE-008):** Core MUST NOT require external analytics success. Hooks are synchronous observers: exceptions are isolated, but callback time adds latency. Each callback receives independent domain data snapshots; ctx is passed unchanged and MUST be treated as read-only. Mutations to domain payloads MUST NOT affect the operation, other callbacks or stored data. This is not an execution sandbox or durable event channel.

## 7. Context

`ctx` is **just an API/Port parameter** — it is NOT a SLDS domain concept.

It does not belong to:
- Identity
- ShortLink
- Lifecycle
- Resolution

It is not a core concept in the SLDS specification. At most, it is mentioned in the Ports/API Contract section:

> `ctx` is a context table passed downward through a single SLDS operation execution. It may carry tenant IDs, trace spans, auth context, or other application-level data. The Repository implementation MAY use it for tenant-aware queries.

## 8. Architecture Boundary

```
                    Application / System
HTTP / OpenResty ──► Host → Namespace
                    Auth / Tenant / Policy
                    Rate Limit / Security
                    Cache / Metrics / Logging
                                   │
                                   │ Identity
                                   ▼
                    ┌──────────────────────────────┐
                    │            SLDS              │
                    │  Identity → ShortLink →      │
                    │  Lifecycle → Resolution →    │
                    │  ResolutionResult            │
                    │  Operations: CREATE/RESOLVE/ │
                    │  UPDATE/DELETE               │
                    │  Hooks / Ports               │
                    └──────────────┬───────────────┘
                     Repository  Generator  Encoder
                                   │
                     Infrastructure
```

### What Belongs to SLDS Core

Identity, Namespace, Code, Target, Lifecycle, Expiration semantics, Resolution, ResolutionResult, Create, Update, Delete, Repository Port, Generator Port, Encoder Port, Hooks.

### What Does NOT Belong to SLDS Core

HTTP, OpenResty, Nginx, Host/Domain, Tenant, User, Authentication, Authorization, Rate Limit, Redis, Cache, SHM, Database, Message Queue, Analytics, Click Tracking, Logger, Metrics, Tracing, Audit, URL Security, Abuse Prevention, Deployment.

### Boundary Test

> "If we remove this capability, does SLDS's Identity/Lifecycle/Resolution semantics still hold? If yes, it probably shouldn't be in Core."

## 9. Core Dependency Constraints

SLDS Core MUST NOT depend on:

```
❌ ngx
❌ ngx.req
❌ ngx.redirect
❌ ngx.header
❌ resty.redis
❌ resty.mysql
❌ lapis
❌ cjson
```

SLDS Core MAY use:

```
✅ Pure Lua (string, table, math, os, etc.)
```

Infrastructure Adapters (outside Core) MAY use:

```
OpenResty / Redis / MySQL / etc.
```

This constraint elevates the project from "yet another short link system" to a portable domain contract.

## 10. Security

### 10.1 Target Validation

SLDS Core SHOULD validate target URL scheme at creation time:

```
❌ javascript:   -- MUST reject
❌ data:         -- MUST reject
❌ file:         -- MUST reject
```

### 10.2 SSRF Prevention

SLDS Core MUST NOT fetch target URLs:

```
❌ Do not HEAD target
❌ Do not GET target
❌ Do not validate whether target exists
```

Fetching the target would introduce SSRF risk into the core.

### 10.3 Open Redirect

Short links are inherently Open Redirects. This is a **product-layer concern**, not a Core bug.

Enterprise environments MAY inject a `TargetPolicy`:

```
policy:validate(target)
```

Allow-list example:

```
*.company.com
github.com
example.com
```

## 11. Metadata

SLDS Core v0.1 preserves an optional `metadata = {}` field on ShortLink.

**Core MUST NOT interpret metadata.**

```
metadata = {
    campaign = "black-friday",
    owner = "marketing",
    source = "internal"
}
```

Metadata MUST be nil or a table. Core copies raw nested table graphs at construction/export/storage boundaries, preserving cycles and shared table relationships within each snapshot and omitting metadata metatables without invoking them. Non-table leaves retain their values; mutable internals of host resources are outside this guarantee. Changes to table snapshots MUST NOT bypass Repository writes. No business schema or deep merge is defined.

Core stores and retrieves. It MUST NOT expose:

```
❌ link.campaign    -- business field, not domain
❌ link.owner       -- business field, not domain
```

## 12. Performance Targets

| Operation | Target | Condition |
|-----------|--------|-----------|
| Resolve | P99 < 5ms | Excluding network, Core pure-memory |
| Resolve (cache hit) | P99 < 2ms | Redis or local cache hit |

These targets assume the Core domain logic itself is trivially fast (microseconds). The bottleneck is always I/O, which is outside Core.
